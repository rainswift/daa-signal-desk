# PRD — 可验收需求

把已确认的 brief 写成研发/研究/风控能直接开工的规格。写前读 [craft-floor.md](craft-floor.md)。若无 brief，先跑一轮精简 `shape`。

## 产出结构

```markdown
# PRD: <名称>

## 1. 背景与问题
## 2. 目标用户与场景
## 3. 成功指标（唯一主指标 + 护栏指标）
## 4. 范围 In / Out
## 5. 用户故事与主流程
## 6. 功能需求（含优先级 P0/P1/P2）
## 7. 数据与信号契约（时点、口径、权威源）
## 8. 状态机与异常
## 9. 风控 / 合规
## 10. 非功能（延迟、容量、权限、审计日志）
## 11. 验收用例
## 12. 里程碑与依赖
## 13. 开放问题
```

## 写作规则

- P0 必须可独立演示一条主路径；P2 不得阻塞 P0 定义。
- 每个功能条目包含：**行为 / 触发 / 数据依赖 / 验收**。
- 涉及下单或持仓变化：写明信号时点 → 可交易时点 → 成交假设（引用 [a-share-rules.md](a-share-rules.md)）。
- 数字默认带：单位、频率、窗口、样本区间。
- 「与某某类似」不够；写差异与不可复制约束。

## 验收用例最低集

1. 快乐路径（主成功指标可观测）
2. 数据延迟或缺失降级
3. 涨跌停 / 停牌 / 不可成交
4. 权限不足或合规拦截（若适用）

## Stop

交付 PRD 后列出开放问题；不擅自扩 scope。需要指标深挖转 `metrics`，数据字段转 `data`，回测门槛转 `backtest`。
